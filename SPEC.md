# Техническое задание. Каталог спецификаций СЭДО СФР

Редакция ТЗ 1.0 • Исследование 12 ноября 2026 года • Целевая площадка — GitHub Pages с автономной поставкой для Windows.

## 1. Результат для пользователя

Бухгалтер, аналитик или разработчик вводит номер сообщения, выбирает контур и редакцию, затем открывает справочник XML-полей. Для каждого поля он может установить его полное положение в сообщении, тип, ограничения и источник условия заполнения. Например, для сообщения 10110 путь к периоду трудового договора зависит от ветки занятости. Поиск по одному имени `end` обязан сохранять контекст каждого результата.

Первая поставка сайта должна содержать все обнаруженные позиции общих перечней и отдельные карточки для подтвержденных схем. Образец поведения просмотрщика — существующий локальный справочник 10110. Номер сообщения сам по себе недостаточен для идентификации редакции. Публичная ссылка на конкретную редакцию должна сохранять смысл после следующих обновлений.

### Наблюдения, влияющие на реализацию

* Для 10110 в продуктиве указан Том 16 версии 3.0 от 19.09.2026, в тесте — 3.0.4 от 13.08.2026. У обоих корень `benefitResponse` и пространство имен с суффиксом `v3.0`. Хеши содержимого корневой XSD и всех ее достижимых зависимостей совпадают для исследованной пары. Две карточки редакций всё равно необходимы.
* Совпадение схем не универсально. У 13 из 28 пар различается хотя бы один файл достижимого набора XSD. Это проверка байтов, в том числе аннотаций и форматирования. Структурное изменение полей можно утверждать после сравнения нормализованных деревьев.
* У сообщений 11000 и 11010 корневой тег называется `paymentStatusNotice`. Искать XSD исключительно по имени тега нельзя. Рабочее сопоставление учитывает контур и полное пространство имен из тома.
* Номер 14 встречается в нескольких разделах общего перечня. Строки нужно сохранять с принадлежностью к модулю. Список сообщений для пользователя образуется объединением реестра и отдельных томов: например, в продуктивном комплекте есть отдельный Том 16 для 10110, хотя в извлеченных числовых строках общего перечня этой записи нет.
* Нельзя принимать версию архива, спецификации сервиса или дату проверки страницы за дату ввода сообщения. У продуктивного 7810 таблица истории для версии 3.1 указывает публикацию 08.06.2025 и начало действия 08.06.2026, а ссылка тома подписана 08.06.26. Сохранить значения раздельно и показать расхождение редактору. В ряде тестовых ссылок дата обрезана; неизвестная дата хранится как null.
* Два архива на контур покрывают ЕЦП-модули возмещений и ВНиМ/ССВ. В каталогах также опубликованы служебные спецификации, ЭЛН, ИИС, документы «Соцстрах», РУСТ, МЧД, доходной части, субсидирования и другие материалы. Один файл может описывать множество сообщений. Дата окончания тестирования из новостного объявления не определяет статус каждой схемы.

## 3. Пользовательские сценарии

| Экран | Действия | Критерий результата |
|---|---|---|
| Каталог | Ввод полного или неполного номера, названия, фильтр модуля и контура | Точное числовое совпадение первым. Видны название, модуль, доступные контуры и наличие схем |
| Редакции | Выбор номера, далее контура и записи | По умолчанию открыт продуктив, тест доступен явно. При наличии только теста это видно до открытия. Указаны версия тома, дата, состояние подтверждения и источник |
| Дерево | Раскрытие узлов, выбор ветки, просмотр карточки, копирование пути | Показаны только поля выбранной редакции. Одинаковые локальные имена в разных ветках остаются отдельными результатами |
| Поиск по полям | Поиск по тегу, пути, русскому описанию и значениям перечислений | Из результата можно раскрыть родителей. Сохраняется выбранная редакция и можно вернуться к списку результатов |
| Только документы | Открытие сообщения из перечня без подтвержденной XSD | Показаны доступные официальные документы, модуль, состояние «Есть описание, схема не сопоставлена». Отсутствие XSD не скрывает номер |
| Прямая ссылка | Открытие или отправка ссылки на редакцию и путь | После перезагрузки открывается тот же узел. Неизвестная редакция дает понятное сообщение и ссылку на список редакций |

Редакции сортировать по достоверной дате внутри контура. При отсутствии даты показывать «Дата не установлена». «Последняя обнаруженная» и «Действует на дату» — отдельные признаки. Последний вывод допустим по подтвержденному интервалу действия. Кнопки «Назад» и «Вперёд» браузера должны работать на всех трех экранах.

## 4. Модель данных и история

| Сущность | Обязательные сведения | Правило |
|---|---|---|
| Публикация источника | Контур, система/раздел, URL страницы и файла, исходное название, MIME/вид, SHA-256, время наблюдения | Повторное появление тех же байтов сохраняет историю наблюдений без дублирования содержимого |
| Позиция перечня | Строковый номер, официальное название, описание, модуль, приложение, ссылка на точную версию перечня | Сохранять несколько принадлежностей одного номера; не выводить направление обмена или родство со старым номером из его цифр |
| Редакция сообщения | Идентификатор, номер, контур, версия и хеш документа, дата публикации, начало/конец действия, корневой QName, хеш набора XSD, признаки достоверности | Независимая неизменяемая запись. Новые байты документа или зависимой XSD создают новую редакцию. Поле для неизвестных данных — null |
| Артефакт схемы | URL и SHA-256 ZIP, путь внутри ZIP, версия схемы по таблице документа, `targetNamespace`, список импортов и хешей | Учитывать достижимые зависимости, отделять изменение упаковки ZIP от изменения схемы сообщения |
| Поле | ID в конкретной редакции, родитель, порядковый номер, QName, путь, вид узла, тип/базовый тип, кратность, группы и альтернативы, ограничения, аннотации | Путь — пользовательский адрес. Для неоднозначных путей служебный ключ должен различать структурный контекст и пространства имен |
| Правило из документа | Текст, статус проверки, версия документа, пункт/таблица, привязанные пути | Номер страницы указывать при проверенной пагинации данной редакции; номер пункта хранить независимо |
| Журнал | Время успешной проверки и попытки, хеш снимка, изменения, ошибки, отметка проверки | Исчезнувшая ссылка отмечается как отсутствующая в новом снимке. Предыдущие подтвержденные редакции доступны |

Версия тома и XSD могут находиться в отношении многие-к-одному. Историческая строка в DOCX подтверждает факт упоминания редакции. Если её исходные файлы отсутствуют, показывать «Упомянута в истории, дерево недоступно». Подстановка современного дерева в историческую карточку недопустима. Идентичные деревья разных контуров можно хранить один раз при независимых ссылках на источники.

## 5. Требования к разбору схем и отображению

1. Найти в томе таблицу структуры, извлечь имя корня, namespace и путь. Найти единственный глобальный элемент с таким QName в материалах того же контура. Сверить путь с учетом префикса каталога архива и регистра для диагностики. При неоднозначности направить запись на проверку с перечнем кандидатов.
2. Разбирать XSD с учетом пространства имен, локальных/global объявлений, `elementFormDefault`, `attributeFormDefault`, локального `form`, `ref` и типов. Разрешать `import/include` относительно текущего файла. Не выполнять сетевые обращения по ссылкам внутри XML. Неполный набор зависимостей должен быть виден в отчёте.
3. Сохранять порядок `sequence`, семантику `all`, выбор и вложенность `choice`, кратность групп и кратность элементов. Представить атрибуты и точки расширения `any/anyAttribute`. Для циклических типов предусмотреть ссылки с ленивым раскрытием или явно пометить неподдержанный тип.
4. Для простых типов показывать значения перечислений с аннотациями, длину, шаблон XSD, включительные и исключительные границы, общее и дробное число знаков. Различать `fixed`, `default`, `nillable`, отсутствие элемента и нулевое значение. Для отмечаемых ограничений сохранять источник объявления и наследование.
5. Показывать «Обязателен внутри родителя» и кратность в пределах альтернативы. Рядом приводить текстовые условия из аннотаций элемента и связанных блоков. Например, `end` может иметь `minOccurs=0`, хотя по аннотации для определенного договора дата обязательна. Приложение служит справочником; проверка готового XML и бизнес-валидация СФР в первый выпуск не входят.
6. В интерфейсе доступны путь, имя XSD-файла, источник типового определения, ссылка на официальный том и конкретную редакцию. Формулировки из DOCX, из XSD и редакторские пояснения должны быть различимы. Загруженные описания выводить как текст.

## 6. Обновление и выпуск на GitHub

Предлагаемая структура репозитория: сборщики в `tools/`, неизменяемые снимки в `state/snapshots/`, исходные архивы схем по хешу в `state/objects/`, маршруты каталога и нормализованные поля в `data/`, приложение и артефакт публикации в `site/` и `dist/`. Рабочий комплект из приложения к ТЗ использует скрипты в корне; его файлы можно перенести в `tools/` вместе с локальными импортами.

1. Запуск по кнопке GitHub Actions. Для эксплуатации предусмотреть настраиваемый график, например один раз в сутки. Два запуска с записью состояния должны сериализоваться.
2. Прочитать страницы обоих контуров, исключить закомментированные ссылки, разрешить относительные адреса, сохранить снимки и контрольные суммы. Загружать известные виды материалов и учитывать новые виды как требующие классификации.
3. Сверить содержимое по SHA-256. Идентичный повтор не создает редакцию. При смене байтов под прежним URL сохранить оба состояния. Исчезновение номера не удаляет его историю. Если ресурс отдал страницу ошибки вместо DOCX/ZIP, оставить предыдущую подтвержденную публикацию.
4. Для каждого контура сформировать перечень и карточки из томов, построить граф зависимостей, затем деревья. В отчёте по изменениям показать документ, номер, контур и вид изменения: добавление, новая редакция, пропавшая ссылка, несопоставленная схема, измененные теги/ограничения. Отделить изменения аннотаций от изменений допустимых значений.
5. Сформировать проверяемый кандидат. При конфликте дат, неоднозначном корне, неизвестной конструкции, массовом исчезновении ссылок или ошибке чтения не заменять действующий публичный сайт. Хранить машиночитаемый отчет и пригодные для повтора исходные файлы.
6. Редактор проверяет diff и утверждает изменения в репозитории. Состояние успешных сборок хранится в версионируемом хранилище; временный artifact Actions не является единственной копией истории. Откат — развёртывание предыдущего проверенного коммита вместе с его индексами.
7. Для сайта использовать GitHub Pages с относительными URL, включая размещение в подпути репозитория. Для прямых ссылок использовать hash-маршрутизацию. Загружать только каталог и выбранное дерево. Для локальной поставки предусмотреть встроенные данные или JS-модули данных, работающие через file:// без fetch к локальным JSON. Приёмка включает режим без сети.
8. Для публикации — отдельная задача с окружением `github-pages` и правами `pages: write`, `id-token: write`; сборщику достаточно чтения репозитория. Предоставленный workflow выполняет сбор кандидата с правами чтения. Развёртывание относится к этапу реализации сайта. [Документация GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)

## 8. Готовность и этапы

**Уже поставляется.** Снимок источников, список 242 числовых строк общих перечней с контекстом, 56 сопоставлений и JSON-деревья, локальный скрипт обновления, автономная пересборка из сохраненных XSD, пример ручного workflow GitHub Actions. Для 10110 в каждой исследованной редакции собрано 520 позиций. Инструкция запуска — в комплекте.

**Следующий этап — интерфейс.** Реализовать каталог и список редакций, подключить нынешний просмотрщик к выбору данных, ввести устойчивые URL, подготовить offline-выпуск и проверить сценарии 1–4 и 10. Третьим этапом добавить построчное сравнение версий, проверку дат, редакторский процесс, сохранение утвержденного состояния и развёртывание Pages.

**Ограничения прототипа.** Автоматическое сопоставление ориентировано на конкретную структуру исследованных HTML, DOCX и XSD. История начинается с первого сохраненного снимка. Скрипт не извлекает все бизнес-правила из произвольного текста Word, не восстанавливает старые XSD из таблиц истории, не проверяет юридическую применимость схем и не выставляет статус «действует». Новые виды составных типов, локальные переопределения namespace/form и нетиповые компоновки таблиц требуют отдельной приемки. Фактическое выполнение workflow на GitHub и публикация сайта в эту поставку не входят.
