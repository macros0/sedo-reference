# Ежедневный сбор WSDL/XSD через SourceCraft

[SourceCraft](https://sourcecraft.dev/alexey-sagitov/sedo-xsd-collector) запускает
`sfr-daily` в **07:00 по Москве** (`0 4 * * *`, UTC). Продуктивный и тестовый контуры
собираются последовательно. GitHub запускает Check SFR catalogs в **07:17 по Москве**:
`python sourcecraft_pull.py` получает снимки перед существующим импортом документов.
Возможны обычные задержки запуска CI; обе задачи доступны также для ручного запуска.

## Паузы и сбои

Один запрос одновременно; минимум 5 секунд после окончания предыдущего; таймаут
30 секунд; одна попытка. После первой ошибки (включая 403, 429, 503 и таймаут)
новых запросов нет, в том числе по альтернативным адресам и следующему контуру.
`Retry-After` сохраняется в отчёте. Бюджет сборщика — 32 запроса, CI — 10 минут.
Это консервативные настройки проекта, а не официальный разрешённый лимит СФР.

В существующем импорте DOCX/ZIP GitHub включает `SEDO_SFR_POLITE=1`: все рабочие потоки
используют одну очередь с теми же паузами и остановкой при первой ошибке; бюджет
каталога — 1000 запросов. Отдельная живая проверка WSDL перед Pages убрана.

Если любой контур не собран полностью, новая публикация SourceCraft не создаётся.
Старые успешные данные остаются доступны. Ошибка чтения или проверки входов в GitHub
останавливает обновление, опубликованный справочник сохраняется. Проверка HTTPS включена.

## Хранение и получение

Ветка `main` SourceCraft содержит код и cron. Отдельная ветка `snapshots` содержит:

- `objects/<SHA-256>` — исходные WSDL/XSD и архивы;
- `collector/<prod|test>/<content_id>.json` — неизменяемые манифесты;
- `index.json` — всю историю и указатели текущих наборов.

Новые наборы добавляются, старые не удаляются. Неизменный набор не создаёт коммит.
При возврате к прежнему содержимому меняется только указатель текущего набора;
первый манифест и его дата сохраняются. Публикация только fast-forward; конфликт
публикации завершается ошибкой, без force push. Push в snapshots не запускает новый сбор.

GitHub фиксирует commit SHA ветки snapshots, читает публичные RAW-файлы этого коммита,
скачивает только отсутствующие манифесты и объекты, проверяет SHA-256, content_id,
контур, размеры и полное замыкание импортов офлайн. Повреждённая пачка отклоняется до
записи. `state/collector/feed.json` определяет текущий набор, включая возврат к старому.
История редакций, исходные DOCX и прежние деревья сохраняются существующим механизмом.

Индекс каждого проверяемого коммита читается одним запросом (до 2 МиБ).
Общий лимит запуска на недостающие манифесты и объекты составляет 256 запросов
и 128 МиБ. При достижении лимита `sourcecraft-report.json` получает значение
`true` для поля `resumable`. Следующий запуск продолжает загрузку
закреплённого коммита из `.sourcecraft-import/`, пока SHA-256 подтверждённого
индекса совпадает. При ошибке проверки или отсутствии файлов закреплённого
коммита сборщик может один раз перейти к новой вершине ветки в пределах
того же бюджета. В Actions каталог восстанавливается из кэша по коммитам
основной ветки с тем же подтверждённым индексом. При отсутствии кэша
загрузка начинается заново. Старый указатель действует до проверки SHA-256
и замыканий XSD всей партии.

Предел одного сериализованного манифеста составляет 16 МиБ при публикации и
чтении. Это позволяет прочитать прежние манифесты с описаниями схем объёмом
свыше 1 МиБ. Размер сохранённых загрузок ограничен 512 МиБ и 100 000 файлами. Сумма
размеров манифестов, исходников и их архивов при офлайн-проверке истории
ограничена 2 ГиБ на коммит. Превышение одного из этих пределов требует
пересмотра объёма поставки или настроек. Причина указывается в отчёте.

GitHub-токен в SourceCraft не нужен. Запись своей ветки использует временный
`SOURCECRAFT_TOKEN` из CI; токен передаётся Git через окружение и не пишется в файлы
и журналы. Публичное чтение GitHub не требует SourceCraft-токена.

## Проверка и восстановление

Ручной запуск: SourceCraft CI/CD → sfr-daily на main, затем GitHub Actions →
Check SFR catalogs → Run workflow. Отчёт SourceCraft: артефакт `results/daily-report.json`.
Отчёт получения GitHub: `sourcecraft-report.json` в артефакте `sfr-update-report-<номер попытки>`.
Результат публикации проверяется в Publish reference. Не запускайте несколько сборов одновременно.

Общие модули collector.py, collector_snapshots.py, collector_feed.py,
collector_transport.py, sync.py, wsdl_sources.py, schema.py и публичные certs/ обновляйте
согласованно с основным проектом. Пользовательские XML и токены не добавляются.

После проверки новой цепочки домашний sedo-collector.timer выключается, чтобы не
дублировать обращения. Код и архивы домашнего сборщика остаются для восстановления
по [прежней инструкции](russian-collector.md). Перед его включением остановите
расписание SourceCraft, чтобы два сборщика не обращались к СФР одновременно.

Для переключения на резерв обновите скрипты в контейнере по прежней инструкции и выполните
один успешный домашний сбор обоих контуров. Убедитесь, что в GitHub появились файлы
`state/collector/prod/current.json` и `state/collector/test/current.json`. Затем в GitHub →
Settings → Secrets and variables → Actions → Variables задайте переменную репозитория
`SEDO_COLLECTOR_SOURCE` со значением `home` и запустите Check SFR catalogs.
Проверка пропустит загрузку SourceCraft и использует подтверждённый домашний указатель
каждого контура. При отсутствии указателя проверка останавливается. Для локального
запуска используется одноимённая переменная окружения. Первая карточка на сайте
показывает обработку домашних снимков и время проверки GitHub.

При возврате остановите домашний таймер, включите расписание SourceCraft и дождитесь
его успешного сбора. Удалите переменную репозитория или задайте значение `sourcecraft`
и повторно запустите Check SFR catalogs. У каждого сборщика собственные указатели,
поэтому возврат любого из них к более раннему содержимому учитывается независимо.


## Статус на сайте

SourceCraft записывает результат каждого запуска в отдельную ветку `status` (status.json), включая неизменные схемы и неудачные/прерванные сборы. Манифесты `snapshots` при этом остаются неизменяемыми. Время проверки берётся из текущего запуска, а не из даты первого сохранения схемы; сохранён также последний успешный результат.

GitHub workflow **Refresh automatic update status** запускается в 07:05 МСК и при запуске/завершении **Check SFR catalogs** и **Publish reference**. Он читает реальный результат SourceCraft, Actions и отчёты импорта, публикуя компактный status.json в отдельную ветку `automation-status`. Это не вызывает повторную сборку Pages и позволяет сообщить об ошибке, даже если новая версия сайта не развернулась. При недоступности самой задачи статус станет устаревшим (порог 36 часов).

Проверка записывает ожидаемый коммит и SHA-256 каталога в publication-target.json. Статус сопоставляет их с квитанцией той попытки Pages, которая выполнила deploy. Повтор задания refresh-status сохраняет результат и время подтверждённого развёртывания. Для старых запусков применяются прежние признаки, включая совпадение checked_at каталога с отчётом обновления. Изменение WSDL/XSD и новые редакции сообщений показываются отдельно.

Браузер читает только публичный JSON из ветки automation-status, без токенов и пользовательского XML. Кнопка обновления статуса не запускает CI и не обращается к СФР. Ручное обновление служебного отчёта доступно владельцу в Actions → Refresh automatic update status → Run workflow.

В карточках указаны ближайшие плановые запуски SourceCraft (ежедневно 07:00 МСК) и забора GitHub (07:17 МСК). Браузер рассчитывает будущую дату при открытии страницы и обновлении статуса, независимо от даты последнего отчёта и часового пояса посетителя. Плановое время не гарантирует точный момент старта CI. При изменении cron в `.sourcecraft/ci.yaml` сборщика или `.github/workflows/check-sfr.yml` обновите соответствующее UTC-время в `dailyRuns` файла `web/automation-status.js`.
