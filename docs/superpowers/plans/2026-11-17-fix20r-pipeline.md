## Реализация

1. `update_catalog.main` проверяет массовое исчезновение публикаций перед установкой как при сетевом обновлении, так и при `--offline`, когда есть прошлый каталог. Первое построение не требует базы сравнения. Регрессия моделирует исчезновение 3 из 3 и побайтную сохранность каталога/индекса; отдельная проверка разрешает штатный вывод 1 из 2.
2. Inbox передаёт прежние поля как отдельные `reset_fields` и прежний ID записи пути. `stage_import` применяет сброс только к совпавшему ID выбранного дубликата; явно заданные новые поля применяются независимо. Покрыты замена DOCX, замена ZIP, сохранение названия найденной другой редакции и снятие названия с той же редакции.
3. Общий `import_structure` выбирает ровно одну `module_bindings` по явно заданному номеру до предварительного выбора ZIP и до вывода редакции. Признак формата `document_type=module` отделён от `source_type=manual`; `schema_review` направляет такой документ в модульный аудит. Оригинальные архивные документы №14/701 проходят collect → stage → повторный импорт → модульный аудит. Неправильный номер и две разные подходящие схемы отклоняются.
4. Имя файла в `catalog` извлекается через `urlsplit(...).path`; источник сохраняет полный URL. Параметры со слешем, фрагменты и ложный номер в query не влияют на номер/приложение.
5. DOCX с шапкой и одной допустимой строкой включается в реестр. Пустая шапка остаётся пустой. Старый разбор таблиц сохраняется для явного replay форматов <7.
6. Общий `cell_text` сохраняет границы абзацев, `w:tab`, `w:br`/`w:cr` как пробелы, не разрывает слова между formatting runs. Для новых снимков при отличиях ставится `docx_text`, поднимающий формат до 7 совместно с `included_roots`. Явное воспроизведение форматов <7 использует прежний парсер. Исторические snapshot, события, даты, `update_sources` и `source_observations` сохраняются. Новое производное поле `document_display[sha] = {document_history: [...], text_replacements: {exact_legacy_string: corrected_string}}` хранит строки, пересчитанные из проверенного оригинального DOCX. Отображаемые поля текущих редакций/реестра поправляются отдельно; намеренные ручные названия сохраняются. Коррекции групп реестра распространяются на редакции только по совпадению исходного значения. Если ранее история отсутствовала в снимке, иммутабельный источник восстанавливается старым способом; каноническая история хранится отдельно для показа.
7. Актуальность сопоставления в `_export` определяется парой SHA-256+URL и сообщением/контуром текущего снимка. Исторический успех A не скрывает действующий несопоставленный A, когда текущий B с теми же байтами готов.
8. Оба пути домашнего сборщика проверяют содержимое существующей квитанции, даже если остальные входы неизменны. Испорченная дата восстанавливается только по `processed.sources.home` с подтверждённым временем; при отсутствии домашнего свидетельства отказ происходит до записи/публикации. Дата общей оболочки/SourceCraft не используется. Отсутствующая первая квитанция может брать время текущего успешного домашнего сбора. Исправная первая дата сохраняется при повторе. Проверки включают локальную сохранность всех байтов при отказе и чтение восстановленной истории.

## Уточнения заключительного ревью

Локальные 257 байт и недоступный GitHub blob воспроизведены red; оба пути затем прошли green. Без домашнего ledger исходные файлы/дерево сохраняются и возвращается ошибка. Старые форматы сохраняют прежнее извлечение basename, включая прежние ошибочные номера из query: это необходимо для сохранности уже подтверждённых редакций и дат первого наблюдения. Свежий сбор с query/fragment у DOCX отмечает `docx_url` и формат 7. Выбор индивидуальных документов в collector replay использует формат исторического baseline.
- Полный регрессионный сценарий создал старый формат 6 с `guide.docx?download=Тип_сообщения_701`, экспортировал подтверждённую редакцию 701 и успешно выполнил `--offline` после исправления с равными событиями и источниками. Новый снимок `Тип_сообщения_999.docx?r=/foo` получил формат 7 и номер 999. До исправления тест терял старую 701.
- Предварительный выбор ZIP в inbox и вывод каталога используют общий `prefer_schema_location`: явный путь Word выбирается до группировки dependency closures. В регрессии `main.xsd` включает `common.xsd`, оба индексируют один root; collect → stage выбирает явно названный `main.xsd`. До исправления collect отказывал с неоднозначностью.

## Повторное заключительное ревью: алиасы и исторический replay

- Маркер `docx_url` перенесён с представителя скачивания на все успешно загруженные URL-алиасы. Реальный сбор пары `guide.docx` / `guide.docx#Тип_сообщения_701` в обоих порядках ссылок теперь создаёт формат 7 и не выдаёт ложный номер 701. Явный replay формата 6 сохраняет прежний результат 701; число физических скачиваний остаётся равным одному. Регрессия получена red → green.
- Подтверждённая домашняя запись ledger со статусом `recorded` принимается как свидетельство для восстановления квитанции наряду с `replayed`/`unavailable`; применяется та же проверка даты с часовым поясом. Использована фактическая форма записи с полями `status`, `snapshot`, `observed_at`; red → green.
- У общего тестового `document(title)` добавлен необязательный номер `number='999'`. Фикстуры входящих 991–993 и 9997 теперь объявляют свой фактический номер внутри Word. Требование отклонять неправильный номер модульного документа сохранено. Два BatchBuild-теста, проверка InboxIndex CLI и оба ManualCorrection-теста проверяются повторно.

Регрессия использует настоящий сохранённый формат 6 с query-номером 701, начальную WSDL с его корнем и промежуточную WSDL без этого корня. Параметры legacy schema roots передаются в модульный подбор по формату baseline.

## Исправление контекстных модулей после Chromium-проверки

Первоначальная привязка отображаемого модуля по номеру сообщения была неверной: общий реестр содержит №14 в нескольких разных модулях. Перезапись каноническим модулем по номеру превращала служебные сообщения и РУСТ в «Доходную часть». Этот дефект воспроизведён двумя red-проверками: повторяющийся №14 в синтетическом реестре и действующие архивные источники №14 в prod/test.

Окончательный контракт отображения хранит только точные замены строк: `document_display[sha].text_replacements = {old_full_string: corrected_full_string}`. Извлекаются исключительно названия и группы реестра, а также названия из абзацев объявления сообщения. XML-примеры и произвольные таблицы в карту не попадают. Пересчитываются лишь строки, где прежнее склеивание Word и корректное извлечение дают разные значения. Различающиеся по смыслу подписи нескольких модулей не заменяются друг другом. Коррекция из реестра распространяется на SHA источника только при точном совпадении старой строки. Ручные названия сохраняются. Истории, события, даты и исходные source observations не переписываются.

Неоднозначные старые строки с несколькими возможными корректными вариантами исключаются. Дополнительно проверено, что исключённая неоднозначная строка не получает замену обратно через другой документ общего реестра. ## Последняя проверка границ отображения

Получены ещё два независимых red-сценария и затем green. В одном исправление `ab → a b` в документе №14 ранее меняло исходное, правильно оформленное название `ab` другого документа №701. В другом один DOCX содержал цепочку замен `abc → a bc` и `a bc → a b c`: сырая редакция №14 уже имела исправленное `a bc`, а публичный этап применял следующую замену второй раз.

Окончательные ограничения:

- Исправление названия применяется исключительно по собственному исходному DOCX. Между документами распространяются только названия групп модулей и только по полному ключу `(environment, number, field, exact_old_string)`.
- Если собственный DOCX подтверждает строку как неизменённую либо неоднозначную, внешняя замена не добавляется. Эти внутренние свидетельства удаляются из сериализуемых карт.
- Выведенные редакции, реестр и документальные источники отмечаются `display_metadata_applied=True`; признак переносится в текущие edition_sources через SOURCE_KEYS. Исходные source observations и источники событий остаются без этого признака и с исходными строками. Сериализатор публичного представления удаляет признак и не применяет замены к уже обработанной строке.
- Ручные снимки явно исключают этот производный признак при сохранении; он не становится частью оригинального свидетельства.

Обе новые регрессии проходят (2 теста, 0,072 с), включая путь оригинальный ZIP/DOCX → сохранённый снимок → export → group_editions → public serialization и проверку названий edition_sources.
